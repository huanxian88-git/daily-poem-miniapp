### 4.2 1期架构的扩展预留设计

为确保2期扩展不返工，1期在以下层面做预留：

#### 4.2.1 数据模型预留

```python
# 1期已预留，2期直接使用的字段

# Poem模型
class Poem:
    # ... 现有字段 ...
    status: str = "active"           # ← 预留：active/draft/audit_fail
    audit_note: str | None           # ← 预留：AI场景审核备注
    source: str = "manual"           # ← 预留：manual/api/import

# DailyRecommendation模型
class DailyRecommendation:
    # ... 现有字段 ...
    is_pinned: bool = False          # ← 预留：运营强制推荐
    pin_operator: str | None         # ← 预留：操作人

# User模型
class User:
    # ... 现有字段 ...
    is_banned: bool = False          # ← 预留：封禁标记
    ban_reason: str | None           # ← 预留：封禁原因

# 新增：1期建表但2期才用的模型
class FeatureFlag:
    id: uuid
    key: str                         # 功能开关key
    value: jsonb                     # 开关配置值
    description: str                 # 说明
    created_at: datetime

class AuditLog:
    id: uuid
    operator: str                    # 操作人
    action: str                      # 操作类型
    target_type: str                 # 操作对象类型
    target_id: uuid                  # 操作对象ID
    detail: jsonb                    # 变更详情
    created_at: datetime
```

#### 4.2.2 API版本预留

1期所有API使用 `/api/v1/` 前缀，2期运营后台API使用 `/api/admin/v1/`：

```
/api/v1/*          → 1期：小程序端接口（微信JWT鉴权）
/api/admin/v1/*    → 2期：运营后台接口（Admin JWT鉴权，独立账号体系）
/api/internal/*    → 预留：内部服务间调用（无需鉴权，VPC内网）
```

#### 4.2.3 事件埋点预留

1期在关键业务节点输出结构化日志，2期接入数据分析平台：

```python
# 1期代码中统一使用loguru输出事件日志
import structlog

logger = structlog.get_logger()

# 示例：背诵完成事件
logger.info("recite_completed",
    user_id=user.id,
    poem_id=poem.id,
    stage="voice",
    score=85,
    is_mastered=True,
    time_spent_seconds=120
)
```

2期只需将loguru输出对接到腾讯云CLS（日志服务），即可实现数据看板。

#### 4.2.4 功能开关预留

1期引入FeatureFlag模型但仅用于少量开关（如"是否显示课本卡片"），2期扩展为完整的A-B实验框架：

```python
# 1期：简单的功能开关查询
async def is_feature_enabled(key: str, user_id: str = None) -> bool:
    flag = await db.get(FeatureFlag, key=key)
    if not flag:
        return False
    # 2期扩展：支持用户分桶、百分比灰度等
    return flag.value.get("enabled", False)
```

## 七、AI团队效能排期（寇豆码版本）

> 以下排期基于 AI 工程师（寇豆码）的实际产出能力重新评估。基准：每次对话轮次可生成 500-1500 行代码，业务逻辑代码需 2-3 轮迭代验证，模板化代码（模型/API/配置）一轮完成。

### 7.1 AI vs 人类效能对照

| 维度 | 人类中高级开发者 | AI工程师（寇豆码） | 倍率 |
|------|-----------------|-------------------|------|
| **代码生成速度** | 200-400行/天 | 800-1500行/轮 | 3-5x |
| **模板化代码**（模型/API/Schema/配置） | 0.5-1天/模块 | 1轮/模块（~10分钟） | 5-8x |
| **业务逻辑代码**（推荐算法/背诵三关/艾宾浩斯） | 1-2天/模块 | 1-2轮（需迭代验证） | 2-3x |
| **前端页面编写**（小程序原生WXML+WXSS+JS） | 1-2天/页面 | 0.5-1轮/页面 | 3-4x |
| **代码一致性审查** | 需人工review | 内置IS_PASS机制 | N/A |
| **联调能力** | 真机+模拟器均可运行 | **无法运行**，依赖人类配合 | 0x |
| **真机调试** | 可直接操作 | **完全无法替代** | 0x |
| **微信审核/上架** | 按流程操作 | **完全无法替代** | 0x |
| **数据采集**（注释/译文/背景） | 需查资料手写 | 可批量生成，但需人工校对 | 2-3x（产出）+ 校对成本 |
| **错误修复效率** | 定位+修复，可能引入新Bug | 快速定位，但可能遗漏边界case | 2x |
