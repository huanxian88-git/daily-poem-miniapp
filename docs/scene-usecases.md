## 一、文档说明

### 1.1 用途

本文档是「每日背诗」微信小程序的功能场景用例（Scene-Based Use Cases）全集，核心目标：

1. **对齐开发理解**：让工程师（寇豆码）清楚每个功能的边界条件、输入输出和异常处理路径
2. **对齐测试策略**：让QA工程师（严过关）有明确的、可逐条执行的测试用例来源
3. **对齐产品预期**：作为开发与测试对"产品应该是什么样"的唯一事实基准

### 1.2 用例编号规范

```
SC-XXX

SC  = Scene Case（场景用例）
XXX = 三位数字编号，从 001 开始连续递增

模块归属通过"所属模块"字段标明，不体现在编号中以便灵活调整
```

### 1.3 优先级定义

| 优先级 | 含义 | 判断标准 |
|--------|------|---------|
| **P0** | 核心用例 | 不通过则MVP不可交付，影响核心闭环（登录→鉴赏→背诵→成诵→复习） |
| **P1** | 重要用例 | 影响用户体验完整性，但非阻塞上线 |
| **P2** | 次要用例 | 边界场景、极端情况、降级策略 |

### 1.4 与流程图的关系

每个场景用例的"关联流程图"字段指向 `flowchart.md` 中的具体流程节点。建议在阅读本用例时对照流程图理解上下文。

#### 场景 SC-001：首次微信授权登录（正常流程）

- **优先级**：P0
- **用户角色**：未登录访客
- **前置条件**：用户首次打开小程序，本地无 Token，无 USER 记录
- **操作步骤**：
  1. 用户打开小程序
  2. 系统展示品牌启动页（2秒）
  3. 系统检测到本地无有效 Token，展示登录页，页面中央显示"微信登录"按钮
  4. 用户点击"微信登录"按钮
  5. 系统调用 `wx.login` 获取临时 code
  6. 后端用 code 向微信开放平台换取 openid 和 session_key
  7. 前端弹出微信授权弹窗（获取头像、昵称）
  8. 用户点击"允许"
  9. 系统获取头像 URL 和昵称
  10. 后端创建 USER 记录（若 openid 已存在则更新 last_login），签发 JWT（7天有效期）
  11. 前端存储 Token 到本地 Storage
  12. 系统检测该用户无 PROFILE 记录，跳转画像采集页
- **预期结果**：
  - 页面跳转到画像采集页（`/pages/onboarding/index`）
  - 页面顶部显示用户微信头像和昵称
  - 本地 Storage 中存储了 `token` 和 `refresh_token`
  - 后端 USER 表新增一条记录，`last_login` 更新为当前时间
- **异常分支**：
  - 分支A：`wx.login` 调用失败（微信服务异常） → 前端展示 Toast"登录服务异常，请稍后重试"，按钮保持可点击状态
  - 分支B：后端 `code2session` 返回错误（code 过期/无效） → 前端静默重新调用 `wx.login` 获取新 code，最多重试 2 次，若仍失败则提示"登录失败，请重新打开小程序"
- **关联流程图**：flowchart.md → 1. 新用户首次登录流程
- **开发注意点**：
  - `wx.login` 的 code 有效期仅 5 分钟，后端换取 openid 后 code 立即失效
  - openid 是用户的唯一标识，JWT 中应包含 user_id（UUID），不应直接暴露 openid
  - 头像 URL 可能为临时链接，需下载转存到 COS 或定期刷新
- **测试要点**：
  - 验证首次登录后 USER 表 openid 正确写入
  - 验证 Token 7 天后过期
  - 验证拒绝授权后返回登录页

#### 场景 SC-002：已登录用户自动登录

- **优先级**：P0
- **用户角色**：已注册普通用户 / 已完成画像采集的用户
- **前置条件**：用户此前已授权登录，本地 Storage 存在有效 Token
- **操作步骤**：
  1. 用户打开小程序
  2. 系统展示品牌启动页（1-2秒）
  3. 系统检测本地 Token 存在且未过期
  4. 系统携带 Token 调用 `GET /api/v1/user/profile` 验证 Token 有效性
  5. 后端验证通过，返回用户画像数据
  6. 前端根据画像数据判断：
     - 有 PROFILE → 直接进入首页（`/pages/index/index`）
     - 无 PROFILE → 跳转画像采集页
- **预期结果**：
  - 有画像用户：直接进入首页，页面展示今日推荐诗 + 操作栏 + 双入口卡片
  - 无画像用户：跳转画像采集页
  - 无任何弹窗或登录页面闪烁
- **异常分支**：
  - 分支A：Token 已过期 → 后端返回 40101，前端拦截器自动调用 `/auth/refresh` 刷新 Token，静默续期后重试原请求；若 Refresh Token 也过期则跳转登录页
  - 分支B：网络请求超时 → 前端使用本地缓存的用户数据展示首页，Toast 提示"网络不稳定，数据可能不是最新"
- **关联流程图**：flowchart.md → 1. 新用户首次登录流程（"本地Token有效？→是"分支）
- **开发注意点**：
  - 启动页展示时长应可配置（建议 1-2 秒，品牌展示需求）
  - Token 刷新必须在 401 拦截器中静默完成，不能打断用户操作
  - 本地缓存的用户数据应有版本号，避免使用过期数据结构
- **测试要点**：
  - 验证 Token 有效期内多次打开小程序均无登录页闪现
  - 验证 Token 过期（刚好第8天）时的自动刷新行为
  - 验证本地缓存数据与后端不一致时的降级策略

#### 场景 SC-003：Token 过期自动刷新

- **优先级**：P0
- **用户角色**：已注册普通用户
- **前置条件**：本地 Access Token 已过期（超过7天），Refresh Token 仍在有效期内（30天内）
- **操作步骤**：
  1. 用户打开小程序或发起任意 API 请求
  2. 后端返回 40101（Token 过期）
  3. 前端 HTTP 拦截器捕获 40101
  4. 拦截器自动调用 `POST /api/v1/auth/refresh`，携带 Refresh Token
  5. 后端验证 Refresh Token 有效，签发新的 Access Token（7天）和新的 Refresh Token（30天）
  6. 前端存储新的 Token 对
  7. 拦截器用新 Token 重试原始请求
  8. 请求成功返回数据
- **预期结果**：
  - 用户无感知，原始请求正常返回数据
  - 本地 Storage 中 Token 和 Refresh Token 均已更新
  - 新 Token 的过期时间从当前时间起算
- **异常分支**：
  - 分支A：Refresh Token 也已过期 → 后端返回 40102 → 前端清除本地 Token，跳转登录页，Toast 提示"登录已过期，请重新登录"
  - 分支B：并发多个 401 → 拦截器应有防抖机制，多个请求同时触发刷新时只发起一次 `/auth/refresh` 请求，其余请求等待刷新完成后重试
- **关联流程图**：flowchart.md → 1. 新用户首次登录流程（Token有效期规则）
- **开发注意点**：
  - 防抖机制是关键：用 Promise 缓存正在进行的刷新请求，后续 401 共享同一个 Promise
  - Refresh Token 旋转策略：每次刷新后旧的 Refresh Token 应立即失效，防止 Token 被盗后的滥用
- **测试要点**：
  - 验证 401 拦截器静默刷新后原请求正常返回
  - 验证并发 5 个请求同时遇 401 时只发起一次刷新
  - 验证 Refresh Token 旋转后旧 Token 不可用

#### 场景 SC-004：拒绝授权处理

- **优先级**：P0
- **用户角色**：未登录访客
- **前置条件**：用户点击"微信登录"后弹出授权弹窗
- **操作步骤**：
  1. 用户在微信授权弹窗中点击"拒绝"
  2. 系统收到拒绝回调
  3. 页面停留在登录页，"微信登录"按钮上方显示提示文字"需要授权头像和昵称才能使用每日背诗"
  4. 用户可再次点击"微信登录"重新触发授权
- **预期结果**：
  - 页面停留在登录页
  - 提示文字为淡金 `#9A8A6A`，字号 13px，位于按钮上方 16px 处
  - "微信登录"按钮保持可点击状态
- **异常分支**：
  - 分支A：用户连续拒绝 3 次 → 展示更详细的说明弹窗"授权后我们将根据你的偏好推荐诗词，头像仅用于个人页面展示" + [去授权] [暂不]
  - 分支B：用户在系统设置中关闭了微信授权 → `wx.getUserProfile` 返回失败，提示"请在微信设置中允许获取个人信息"
- **关联流程图**：flowchart.md → 1. 新用户首次登录流程（"用户授权？→拒绝"分支）
- **开发注意点**：
  - 微信新版隐私协议下，`wx.getUserProfile` 需用户主动点击按钮触发
  - 不能自动弹出授权窗，必须由用户点击行为触发
  - 拒绝次数计数器存储在本地，每次冷启动重置
- **测试要点**：
  - 验证拒绝后按钮仍可点击
  - 验证连续拒绝3次后弹窗文案正确
  - 验证系统设置关闭授权后的提示文案

#### 场景 SC-005：登录接口超时

- **优先级**：P1
- **用户角色**：未登录访客
- **前置条件**：用户点击"微信登录"，网络状况不佳
- **操作步骤**：
  1. 用户点击"微信登录"
  2. 前端调用 `POST /api/v1/auth/login`，请求超过 10 秒未返回
  3. 前端展示加载中状态（按钮显示 loading 动画）
  4. 15 秒后请求超时
  5. 按钮恢复正常状态，Toast 提示"网络连接超时，请检查网络后重试"
- **预期结果**：
  - 登录按钮恢复可点击状态
  - Toast 提示持续 2 秒后自动消失
  - 不跳转任何页面
- **异常分支**：
  - 分支A：后端返回 500 错误 → 前端展示 Toast"服务繁忙，请稍后重试"，不暴露后端错误详情
- **关联流程图**：flowchart.md → 1. 新用户首次登录流程
- **开发注意点**：
  - 前端请求超时时间建议 15 秒（微信小程序默认 60 秒太长）
  - 按钮 loading 动画应为松绿色圆形旋转指示器
  - 超时后不自动重试，避免雪崩
- **测试要点**：
  - 开启飞行模式后点击登录，验证 15 秒超时行为
  - 验证后端 500 时的前端降级展示

#### 场景 SC-006：Token 在有效期最后 1 小时内自动续期

- **优先级**：P2
- **用户角色**：已注册普通用户
- **前置条件**：Token 距离过期时间不足 1 小时
- **操作步骤**：
  1. 用户正在使用小程序
  2. 前端定时检查 Token 剩余有效期
  3. 发现 Token 有效期 < 1 小时
  4. 在用户无感的时机（如页面空闲时）主动调用 `/auth/refresh`
  5. 刷新成功后更新本地 Token
- **预期结果**：
  - Token 有效期延长 7 天
  - 用户无任何感知
- **异常分支**：
  - 分支A：刷新时网络不可用 → 静默失败，等待下次检查（每 30 分钟检查一次）
- **关联流程图**：flowchart.md → 1. 新用户首次登录流程（Token有效期规则）
- **开发注意点**：
  - 定时检查应绑定到 `App.onShow` 生命周期，而非独立定时器
  - 仅在用户活跃时检查（如页面切换），避免后台时浪费资源
- **测试要点**：
  - 模拟 Token 即将过期，验证自动续期
  - 验证断网时静默失败不影响正常使用

#### 场景 SC-007：首次画像采集完整流程

- **优先级**：P0
- **用户角色**：已注册普通用户（首次登录，无 PROFILE）
- **前置条件**：用户刚完成微信授权登录，PROFILE 表无记录
- **操作步骤**：
  1. 系统展示画像采集页，标题"完善画像，让推荐更懂你"
  2. **第1步**：选择年龄段 → 三个选项卡片「少年(<18岁)」「青年(18-35岁)」「中年(>35岁)」，默认无选中
  3. 用户点击"青年"，卡片边框变为松绿色
  4. 点击"下一步"
  5. **第2步**：选择诗词水平 → 三个选项卡片「入门」「进阶」「精通」，默认选中"入门"
  6. 用户保持默认"入门"，点击"下一步"
  7. **第3步**：选择兴趣偏好 → 六个标签「山水」「边塞」「田园」「婉约」「豪放」「咏物」，默认全选
  8. 用户取消"边塞"和"咏物"（点击已选中标签取消），点击"下一步"
  9. **第4步**：是否为学生 → 两个选项「是，我是学生」「否」，默认无选中
  10. 用户选择"否"
  11. 点击"完成"
  12. 系统调用 `POST /api/v1/user/profile` 保存画像
  13. 页面过渡动画后进入首页
- **预期结果**：
  - PROFILE 表记录：age_group=young, poetry_level=beginner, preferences="山水,田园,婉约,豪放", is_student=no
  - 进入首页后展示基于该画像的今日推荐诗
  - 画像采集页不再展示（除非在"我的→设置"中主动进入）
- **异常分支**：
  - 分支A：保存画像时网络异常 → 本地暂存画像数据，Toast"保存失败，请重试"，用户可再次点击"完成"或关闭页面
  - 分支B：用户在第4步选择"是，我是学生" → 进入课本绑定子流程（见 SC-009）
- **关联流程图**：flowchart.md → 1. 新用户首次登录流程（画像采集部分）
- **开发注意点**：
  - 每步可跳过（没有必选项），所有步骤都有默认值
  - 默认值：青年、入门、全部偏好选中
  - 第4步"是否为学生"必须选择才能点"完成"（是/否二选一）
  - 标签选中态：松绿边框 + 浅绿底色 `#EBF5EE`，未选中态：淡金边框 + 白底
- **测试要点**：
  - 验证全部默认值跳过后的画像保存结果
  - 验证第4步不选时"完成"按钮是否 disabled
  - 验证画像保存后二次进入首页不再弹出采集页

#### 场景 SC-008：画像采集跳过部分步骤（使用默认值）

- **优先级**：P0
- **用户角色**：已注册普通用户
- **前置条件**：用户进入画像采集页
- **操作步骤**：
  1. 第1步：不选择年龄段，直接点"下一步"
  2. 第2步：不修改水平，直接点"下一步"（默认入门）
  3. 第3步：不修改偏好，直接点"下一步"（默认全选）
  4. 第4步：选择"否" → 点击"完成"

### 场景 SC-143：未授权访问（无 Token 请求）

- **优先级**：P0

  - 响应体 `{"code": 40101, "message": "未授权，请先登录"}`

- **关联流程图**：架构文档 9.3 接口鉴权方案
- **开发注意点**：

- **测试要点**：

  - 验证 `/auth/login` 不需要 Token

### 场景 SC-144：接口参数篡改（修改其他用户数据）

- **优先级**：P0
- **用户角色**：已完成画像采集的用户
- **前置条件**：用户 A 尝试修改用户 B 的数据
- **操作步骤**：
  1. 用户 A 调用 `PUT /api/v1/user/profile`，请求体中 user_id 改为用户 B 的 ID
  2. 后端从 JWT 提取当前用户 user_id
  3. 对比请求体中的 user_id 与 JWT 中的 user_id
  4. 不一致 → 返回 403
- **预期结果**：
  - HTTP 响应码 403
  - 响应体 `{"code": 40103, "message": "无权操作该资源"}`
  - 不修改任何数据
- **异常分支**：
  - 分支A：请求体不含 user_id → 默认使用 JWT 中的 user_id（允许）
- **关联流程图**：架构文档 9.4 鉴权方案
- **开发注意点**：
  - 所有写操作接口需校验资源归属
  - 用户 ID 从 JWT 中提取，不信任前端传入
  - 背诵记录、收藏等操作同样需归属校验
- **测试要点**：
  - 验证跨用户修改被拦截
  - 验证背诵记录归属校验

### 场景 SC-145：XSS 防护（用户输入过滤）

- **优先级**：P1
- **用户角色**：已完成画像采集的用户
- **前置条件**：用户输入恶意脚本
- **操作步骤**：
  1. 用户在收藏名或自定义背景注释中输入 `<script>alert('xss')</script>`
  2. 前端展示时使用 `<text>` 组件（自动转义 HTML）
  3. 后端存储前对输入做 HTML 实体编码
- **预期结果**：
  - 恶意脚本不被执行
  - 显示为纯文本
- **异常分支**：
  - 分支A：混元生成的场景描述含 HTML 标签 → 后端过滤去除所有 HTML 标签
- **关联流程图**：PRD 8. 非功能需求（安全）
- **开发注意点**：
  - 小程序中 `<text>` 组件默认不解析 HTML
  - 后端使用 `bleach` 或 `html.escape` 清理用户输入
  - API 响应使用 `Content-Type: application/json`
- **测试要点**：
  - 输入 XSS payload 验证不被执行

### 场景 SC-147：用户数据隔离

- **优先级**：P0
- **用户角色**：已完成画像采集的用户

  4. 仅返回用户 A 自己的背诵记录
- **预期结果**：
  - 返回数据仅包含当前用户的记录
